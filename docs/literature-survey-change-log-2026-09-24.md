## 3. Papers added (31)

Each record: authors · year · venue/status · DOI/URL · problem · method · finding (as reported) · relevance · limitation · what it supports · what Codentry may reasonably infer.

**[31] "Evaluating how static analysis tools can reduce code review effort"** — D. Singh, V. R. Sekar, K. T. Stolee, B. Johnson. 2017. IEEE VL/HCC (peer-reviewed). DOI 10.1109/VLHCC.2017.8103456; PDF http://people.cs.gmu.edu/~johnsonb/docs/vlhcc2017.pdf.
Problem: can static analysis pre-empt reviewer comments? Method: PMD 5.5.1 on Java files of 92 PRs from 23 GitHub repositories; two authors manually compared warnings with 274 reviewer comments. Finding: PMD overlapped with nearly 16% of comments; four additional rules suggested. Relevance: static/human overlap is partial. Limitation: Java/PMD only; authors note inter-rater reliability was not measured. Supports: §3. Infer: static analysis covers only part of what reviewers say; not that it is "sufficient".

**[32] "An Empirical Study of Static Analysis Tools for Secure Code Review"** — W. Charoenwet, P. Thongtanunam, V.-T. Pham, C. Treude. 2024. ISSTA 2024. DOI 10.1145/3650212.3680313; arXiv:2407.12241.
Problem: SAST effectiveness on *real code changes*. Method: 815 vulnerability-contributing commits, 92 C/C++ projects, 319 vulnerabilities. Finding: a single SAST warned in vulnerable functions of 52% of commits; prioritizing changed functions with warnings improved precision by 12% and recall by 5.6% and cut initial false alarm by 13%; ≥76% of warnings in vulnerable functions irrelevant; 22% of commits undetected. Relevance: change-level evaluation and noise. Limitation: C/C++, SAST only. Supports: §3, Table 2 (differential). Infer: change-level reporting is an established evaluation frame.

**[33] "Detecting False Alarms from Automatic Static Analysis Tools: How Far are We?"** — H. J. Kang, K. L. Aw, D. Lo. 2022. ICSE 2022. DOI 10.1145/3510003.3510214; arXiv:2202.05982.
Problem: earlier "near-perfect" actionable-warning classifiers. Method: retrospective analysis. Finding: data leakage and duplication; the heuristic warning oracle (compare with a future revision) produced labels that disagree with human oracles; reported performance overoptimistic. Relevance: ground-truth quality for warnings. Limitation: a re-analysis of prior actionable-warning studies (the datasets' languages were not verified here). Supports: §3, §11 gap 6. Infer: any warning-level label needs leak-free splits and human checks.

**[34] "Tracking the Evolution of Static Code Warnings: the State-of-the-Art and a Better Approach"** — J. Li, J. Yang. 2024. IEEE Trans. Software Engineering, vol. 50, no. 3, pp. 534–550 (Crossref). DOI 10.1109/TSE.2024.3358283; arXiv:2210.02651.
Problem: matching warnings across commits. Method (abstract-level): tracking approaches compared; a better approach proposed. Finding: precise tracking is critical for concentrating on recent, actionable warnings. Relevance: differential/identity. Limitation: only the abstract was verified; dataset and results details were not. Supports: §3, gap 4. Infer: warning identity across revisions is a recognized problem.

**[35] "A Large-Scale Collection Of (Non-)Actionable Static Code Analysis Reports"** — D. Kószó, T. Aladics, R. Ferenc, P. Hegedűs. 2025. arXiv:2511.10323 (preprint; "under publication to Nature Scientific Data" per arXiv).
Problem: scarce datasets for actionable-warning research. Method: collection methodology; >1M Java warnings (NASCAR). Finding: dataset and tools released; alert-fatigue framing. Relevance: labeling approach. Limitation: Java; preprint. Supports: §3.

**[36] "Comparison of Static Application Security Testing Tools and Large Language Models for Repo-level Vulnerability Detection"** — X. Zhou, D.-M. Tran, T. Le-Cong, T. Zhang, I. C. Irsan, J. Sumarlin, B. Le, D. Lo. 2024. arXiv:2407.16235 (preprint; no venue in retrieved metadata).
Problem: how SAST tools and LLMs compare. Method: 15 SAST tools vs 12 LLMs on Java, C, Python repositories. Finding: SAST had low detection with relatively low false positives; LLMs detected up to 90–100% but with high false positives; ensembling mitigated both drawbacks somewhat. Relevance: the most direct static-vs-LLM comparison found. Limitation: vulnerability detection, not PR review. Supports: §6, Table 2, gap 2. Infer: motivates *testing* combination; does not establish it for PRs.

**[37] "Study of JavaScript Static Analysis Tools for Vulnerability Detection in Node.js Packages"** — T. Brito, M. Ferreira, M. Monteiro, P. Lopes, M. Barros, J. F. Santos, N. Santos. 2023. IEEE Trans. Reliability. DOI 10.1109/TR.2023.3286301; arXiv:2301.05097.
Problem: how well JS static tools detect vulnerabilities. Method: nine tools, 957 vulnerabilities from npm advisories. Finding: the three best combined detected up to 57.6% at 0.11% precision; many OWASP Top-10 vulnerabilities detected by no tool. Relevance: JS static tools have low recall/precision. Limitation: vulnerabilities only; tools of the time. Supports: §3, Table 2. Infer: expect a six-rule ruleset to detect little; measure, don't assume.

**[38] "Reducing False Positives in Static Bug Detection with LLMs: An Empirical Study in Industry"** — X. Du, J. Feng, Y. Zou, W. Xu, J. Ma, W. Zhang, S. Liu, X. Peng, Y. Lou. 2026. arXiv:2601.18844 (preprint).
Method: Tencent enterprise SAT, 433 alarms (328 FP, 105 TP), three bug types. Finding: manual inspection 10–20 min per alarm; hybrid LLM+static techniques eliminated 94–98% of FPs with high recall; cost $0.0011–$0.12 per alarm. Relevance: LLM as noise filter. Limitation: one company; three bug types. Supports: §3, §6.

**[39] "Sifting the Noise: A Comparative Study of LLM Agents in Vulnerability False Positive Filtering"** — Y. Xiong, T. Zhang. 2026. ISSTA 2026 (per arXiv metadata only; the DOI given there, 10.1145/3832100, **did not resolve in Crossref**); arXiv:2601.22952.
Method: Aider, OpenHands, SWE-agent on OWASP Benchmark, real Java projects, post-cutoff OSS-Fuzz. Finding: agents removed most SAST noise; benefits backbone- and CWE-dependent; aggressive filtering can suppress true vulnerabilities; SWE-agent+Claude Sonnet 4 identified 95.5% of FPs at 95.5% precision on the post-cutoff set vs 36.4% for vanilla prompting. Relevance: trade-offs of filtering; contamination-aware design. Limitation: alerts from SAST tools only. Supports: §3, §6.

**[40] "Automated Code Review In Practice"** — U. Cihan, V. Haratian, A. İçöz, M. K. Gül, Ö. Devran, E. F. Bayendur, B. M. Uçar, E. Tüzün. 2024/2025. ICSE-SEIP 2025, pp. 425–436 (Crossref). DOI 10.1109/ICSE-SEIP66354.2025.00043; arXiv:2412.18531.
Method: Qodo PR Agent in industry; 4,335 PRs (1,568 reviewed), 238 practitioners, surveys. Finding: 73.8% of comments resolved; average PR closure rose from 5 h 52 min to 8 h 20 min; drawbacks included faulty reviews, unnecessary corrections, irrelevant comments. Relevance: noise and cost in practice. Limitation: one organization; "resolved" is not "correct". Supports: §1, §4, §11 gap 3.

**[41] "Understanding the Limits of Automated Evaluation for Code Review Bots in Practice"** — V. Karakaya, U. B. Torun, B. M. Uçar, E. Tüzün. 2026. EASE 2026 (per arXiv comment); arXiv:2604.24525.
Method: 2,604 bot comments labeled fixed/wontFix; G-Eval and LLM-as-judge with Gemini-2.5-pro, GPT-4.1-mini, GPT-5.2. Finding: agreement 0.44–0.62; developer labels reflect workflow pressures, not just quality. Relevance: developer actions and LLM judges are weak ground truth. Limitation: one company. Supports: §4, §5, gap 6.

**[42] "Benchmarking LLMs for Fine-Grained Code Review with Enriched Context in Practice"** — R. Hu, X. Wang, X.-C. Wen, Z. Zhang, B. Jiang, P. Gao, C. Peng, C. Gao. 2025. arXiv:2511.07017 (preprint).
Method: ContextCRBench, 67,910 entries from 153.7K issues/PRs; hunk-level assessment, line-level defect localization, line-level comment generation; 8 LLMs. Finding: textual context helped more than code context; LLMs far from human level. Relevance: localization metric design. Limitation: preprint. Supports: §4, gap 4.

**[43] "Self-Preference Bias in LLM-as-a-Judge"** — K. Wataoka, T. Takahashi, R. Ri. 2024. NeurIPS 2024 Safe Generative AI Workshop (per arXiv comment); arXiv:2410.21819.
Finding: GPT-4 shows significant self-preference; LLMs rate lower-perplexity (more familiar) text higher than humans do. Limitation: dialogue-style judging; workshop. Supports: §5. Infer: a model judging its own output is suspect.

**[44] "Quantifying and Mitigating Self-Preference Bias of LLM Judges"** — J. Yang, Z. Hu, C. Qiu, Z. Deng, X. Jiao, T. Zhou. 2026. arXiv:2604.22891 (preprint).
Method: equal-quality response pairs, 20 LLMs. Finding: advanced capability often uncorrelated, or even negatively correlated, with low self-preference bias; a multi-dimensional strategy cut bias 31.5% on average. Supports: §5.

**[45] "How Well Do Large Language Models Serve as End-to-End Secure Code Agents for Python?"** — J. Gong, N. Duan, Z. Tao, Z. Gong, Y. Yuan, M. Huang. 2024 (rev. 2025). arXiv:2408.10495 (preprint).
Method: 4,900 code samples from four LLMs; GPT-3.5/GPT-4 identify and repair. Finding: >75% vulnerable code on SecurityEval; models cannot precisely identify vulnerabilities in code they generated; poor repair of self-produced code ("blind spots"). Limitation: older models. Supports: §5.

**[46] "An Empirical Study of the Non-determinism of ChatGPT in Code Generation"** — S. Ouyang, J. M. Zhang, M. Harman, M. Wang. ACM TOSEM vol. 34, no. 2, Jan. 2025 (Crossref). DOI 10.1145/3697010; arXiv:2308.02828.
Finding: on 829 problems, zero-equal-output ratios of 75.76% / 51.00% / 47.56% across three benchmarks; temperature 0 does not guarantee determinism. Limitation: ChatGPT, generation not review. Supports: §5, Day-5 plan (repeat runs).

**[47] "Breaking the Silence: the Threats of Using LLMs in Software Engineering"** — J. Sallou, T. Durieux, A. Panichella. 2024. ICSE-NIER 2024. DOI 10.1145/3639476.3639764; arXiv:2312.08055.
Position paper on closed-source model drift, data leakage, reproducibility; proposes guidelines. Limitation: no empirical data. Supports: §5.

**[48] "Guidelines for Empirical Studies in Software Engineering involving Large Language Models"** — S. Baltes et al. (22 authors). Empirical Software Engineering (accepted, per arXiv). arXiv:2508.15503.
Finding/content: taxonomy of seven study types and eight guidelines (declare LLM role; report versions/configurations; document prompt/system design; report session traces; suitable baselines/benchmarks/metrics; include an open LLM baseline; validate outputs against human judgment; articulate limitations). Limitation: guidance, not evidence. Supports: §5, harness protocol.

**[49] "The SWE-Bench Illusion: When State-of-the-Art LLMs Remember Instead of Reason"** — S. Liang, S. Garg, R. Zilouchian Moghaddam. 2025. arXiv:2506.12286 (preprint).
Finding: up to 76% accuracy identifying buggy file paths from issue text alone vs up to 53% on repositories outside the benchmark; 5-gram accuracy up to 35% vs 18% elsewhere. Limitation: issue resolution, not review. Supports: §5 (contamination).

**[50] "SWE-Bench+: Enhanced Coding Benchmark for LLMs"** — R. Aleithan, H. Xue, M. M. Mohajer, E. Nnorom, G. Uddin, S. Wang. 2024. arXiv:2410.06992 (preprint).
Finding: 32.67% of successful patches involved solution leakage; 31.08% suspicious due to weak tests; resolution rate 12.47% → 3.97% after filtering; >94% of issues predate model cutoffs. Supports: §5.

**[51] "Recent Advances in Large Language Model Benchmarks against Data Contamination: From Static to Dynamic Evaluation"** — S. Chen et al. 2025. arXiv:2502.17521 (preprint; arXiv metadata spells "Langauge"; a search index lists a different title for the same identifier).
Content: survey of static-to-dynamic benchmarking; notes the lack of standardized criteria for dynamic benchmarks. Supports: §5.

**[52] "Evaluating SZZ Implementations Through a Developer-informed Oracle"** — G. Rosa, L. Pascarella, S. Scalabrino, R. Tufano, G. Bavota, M. Lanza, R. Oliveto. 2021. ICSE 2021, pp. 436–447 (Crossref). DOI 10.1109/ICSE43902.2021.00049; arXiv:2102.03300.
Finding: SZZ evaluations rely on researcher judgment; proposes an oracle from commits where developers explicitly reference the introducing commit. Supports: §5, Day-3 plan (avoid naive SZZ).

**[53] "Are mutants a valid substitute for real faults in software testing?"** — R. Just, D. Jalali, L. Inozemtseva, M. D. Ernst, R. Holmes, G. Fraser. FSE 2014 (Hong Kong). DOI 10.1145/2635868.2635929.
Method: 357 real faults, 5 open-source programs, 321,000 LOC; developer-written and generated test suites. Finding: statistically significant correlation between mutant detection and real-fault detection independent of coverage; inherent limitations remain. Limitation: about test suites, not reviewers; Java. Supports: §5, Table 2.

**[54] "BugsJS: a Benchmark of JavaScript Bugs"** — P. Gyimesi, B. Vancsics, A. Stocco, D. Mazinanian, Á. Beszédes, R. Ferenc, A. Mesbah. 2019. ICST 2019, pp. 90–101 (Crossref). DOI 10.1109/ICST.2019.00019; https://bugsjs.github.io/. An extended journal version exists (STVR 2020, DOI 10.1002/stvr.1751, per Crossref).
Content (from the project site/search summary; paper not opened): 453 real, manually validated bugs from ten Node.js programs, each with bug report, failing tests, and fixing patch. Limitation: popular repositories → likely training-data overlap. Supports: §5, Day-3 plan.

**[55] "Bigger Isn't Always Better: A Comparative Evaluation of LLMs for Automated Code Review"** — S. P. Kumar, S. Bararia, K. Raj. arXiv:2606.15689 (preprint). **Low confidence.**
Method: five models, 150 samples (100 mutation-injected, 50 real bug-fix PRs). Reported: large F1 drop on real PRs; near-zero recall on performance bugs. **Anomalies:** identifier month 06 vs. submission date 9 April 2026; 7 pages, 13 references. Used only as illustrative support for the mutant-realism concern; not load-bearing.

**[56] "GitInject: Real-World Prompt Injection Attacks in AI-Powered CI/CD Pipelines"** — J. Isbarov, U. Suleymanov, I. Shumailov, M. Kantarcioglu. 2026. arXiv:2606.09935 (preprint).
Finding: eleven named attacks (config-file injection, credential exfiltration, judgment manipulation, availability) across four providers in live GitHub workflows; all susceptible to at least one class by default; the most critical vulnerabilities are structural (credential/config handling). Supports: §7, gap 9.

**[57] "Demystifying and Detecting Agentic Workflow Injection Vulnerabilities in GitHub Actions"** — S. Wang, X. Hou, Z. Liu, Y. Zhao, X. Cheng, Q. Zou, X. Zhang, H. Wang. 2026. arXiv:2605.07135 (preprint).
Finding: 1,033 AI-assisted actions characterized; 13,392 workflows in 10,792 repositories analyzed; 519 potential vulnerabilities, 496 confirmed (precision 95.6%), 343 previously unknown. Supports: §7.

**[58] "Can Adversarial Code Comments Fool AI Security Reviewers — Large-Scale Empirical Study of Comment-Based Attacks and Defenses Against LLM Code Analysis"** — S. Thornton. 2026. arXiv:2602.16741 (preprint; version-1 title; another index lists "LLM Code Reviewers Are Harder to Fool Than You Think").
Finding: eight models, 9,366 trials on a 100-sample benchmark; adversarial comments had small, statistically non-significant effects; among four defenses, static-analysis cross-referencing performed best (96.9% detection, recovering 47% of baseline misses). Limitation: 100 samples; comment-based attacks only. Supports: §6, §7.

**[59] "Automatic Security Assessment of GitHub Actions Workflows"** — G. Benedetti, L. Verderame, A. Merlo. 2022. ACM SCORED workshop. DOI 10.1145/3560835.3564554; arXiv:2208.03837.
Finding: methodology and tool (GHAST) applied to 50 open-source projects found 24,905 security issues. Limitation: workshop paper; earlier era. Supports: §7.

**[60] "The Rise of AI Teammates in Software Engineering (SE) 3.0"** — H. Li, H. Zhang, A. E. Hassan. 2025. arXiv:2507.15003 (preprint).
Content: AIDev dataset, >456,000 PRs by five agents, 61,000 repositories, 47,000 developers; agents faster but accepted less. Limitation: attribution of authorship by dataset heuristics. Supports: §8.

**[61] "AI-to-AI Code Reviews of GitHub Pull Requests"** — N. Selvanayagam, T. A. Ghaleb. 2026 (submitted 2026-08-21). arXiv:2608.21311 (preprint).
Finding: 248,641 AI-attributed PRs with AI-attributed reviews; cross-product review ≈1.6% of identified agent-authored PRs, growing by more than two orders of magnitude from 2025-Q1 to Q3. Supports: §8.
